# 数据、审核与发布操作说明

## 数据接口

- `data/source/videos.jsonl` 是完整原片库，主键 `vid`；原站导出不含时长，匹配时从原站公开视频详情获取核验所需时长，仅存本地缓存。
- `data/work/library.json` 按原片ID保存候选。每个候选以 `bvid` 识别，并记录定位后的 `page`、`cid`、时长、语言类型、依据、检查时间与状态。
- 状态为 `confirmed`（已确认）、`review`（待审核）、`unmatched`（未找到）和 `invalid`（已明确失效）。请求失败单独记录错误，不当作失效。
- 根 `data.json` 是前端接口：`schema_version: 1`，含 `stats`、有内容的 `areas`、`videos` 和旧BV到原片的 `legacy` 映射。该映射仅包含已发布版本；待审候选BV不进入公开数据。视频以 `id` 为主键，`versions` 只包含确认且可用的分P版本；第一项为默认版本。
- 一个原片可有多个BV；同一BV可用不同分P对应不同原片。同一BV同一分P若指向多个原片，构建时全部隐藏，等待纠正。
- `data/confirmed.json` 保存最小确认记录与处理状态用于复现；待审核候选和接口原始内容仅存在本地，不会放入前端数据。

## 一次批量更新

先检查 Git 状态，备份本地 `data/work/`；不要同时运行多个匹配或审核进程。来源刷新会在本地保留上一版快照，Git保存已发布快照。

```sh
python3 scripts/fetch_source.py
python3 scripts/pipeline.py import
python3 scripts/pipeline.py match --limit 50
```

每批上限50条，优先已有候选，再按原站质量分排序。先依次搜索原片标题、作者加标题，每个查询最多取20个候选。串行请求至少间隔1.2秒；使用程序内临时访客会话，不读取本机个人Cookie。API成功响应缓存7天，过期后重新检查。

`match` 默认跳过已完成原片和已检查候选；中断后再次运行会从未完成条目继续。`--existing-only` 仅复核已导入的旧候选，`--recheck` 重新评估已有条目（仍复用未过期缓存）。更新前如需强制刷新某条接口，可移走本地对应缓存；不要清空缓存后大量重试。

HTTP 401/403/412/429及接口风控/登录代码会立即停止批次，退出码2。超时等普通请求错误记录后继续，最后也返回2。查看 `reports/STATUS.md`、`reports/summary.json` 与本地 `data/work/batches/`，解除阻塞后再人工触发。已完成条目不会丢失。

## 对应关系与审核

自动确认必须满足：B站简介明确指向该YouTube原片，分P可定位，原片和分P时长差不超过 `max(60秒, 8%)`，无年份、集次、明显删减或多个原片链接冲突。多P视频必须有对应分P的原片ID或明确分段来源链接；整BV来源加相似分P标题不够。缺少该依据时保持待审，后续复核须保存实际分P级内容或来源证据。相似标题、UP主名相同以及旧“高可信度”都不能单独作为确认依据。

以下流程由执行者真实检查资料或内容后操作，不得编造审核说明：

```sh
python3 scripts/pipeline.py export-review
python3 scripts/pipeline.py inspect 原片ID BV号 --page 2
python3 scripts/pipeline.py review 原片ID BV号 confirmed --page 2 --evidence '具体核验依据：片头作者、讲座名、对应集次及原片来源链接等'
```

`inspect` 获取指定分P详情并重新评估，支持添加手工找到的BV线索。无法定位分P、年份或集次冲突、明显删减的条目不能直接人工放行；先找到正确版本或修正对应数据。待审核和失效也可通过 `review 原片ID BV号 review` 或 `invalid` 标记。人工确认在后续复核中仅在分P的CID不变且没有硬冲突时保留。

选择语言版本时，“官方”字样和UP主与作者同名均不能证明账号归属。官方优先档须同时匹配原作者与 `data/official-channels.json` 中已核实的B站数字账号ID；更名不影响账号ID判断，其他账号保留字幕、配音或原语类别。新增账号须由原作者公开网站直接链接等依据核实并保存来源与日期，不自动凭昵称加入。目前清单中的3Blue1Brown账号由其官网About页面直接链接确认。

## 构建、验证与发布

```sh
python3 scripts/pipeline.py build
python3 scripts/pipeline.py check
python3 -m unittest discover -s tests -v
node --check app.js
```

从本地候选构建；新克隆没有本地库时使用最小确认清单重建。构建复制 `web/` 中三个页面文件到根目录，公开数据不包含个人凭据、内部路径或待审详情。检查桌面和手机上的分类、搜索、版本切换、分P跳转、收藏及嵌入播放，再核对发布数据统计。

发布采用普通提交与普通推送到 `main`，由 GitHub Pages 自动部署；仅在任务授权覆盖发布时执行。推送前先获取远程状态并确认没有他人新增提交，不强推。发布后核对Actions状态、新网址HTTP状态和 `data.json` 的SHA-256与本地一致。

初始回退基线是 `65dfbd6e285e8f793f369b4107281cdc11ef6a03`。普通 `git revert` 对应发布提交可恢复上一版；不要重写历史。远程HTTPS无登录时可使用已配置的GitHub SSH认证，无需复制令牌。

## 当前限制

原站与B站元数据可能过期；简介链接和时长核验无法保证所有画面相同。真实播放抽查按验收报告记录，不把测试播放器地址成功当成视频已播放。分类翻译是本项目维护的展示层，保留原站ID以便增量更新。

取消时长门槛后，新匹配流程会正常处理短视频；首批旧候选主要是长视频，短视频覆盖需要后续批次。项目不运行定时任务，不承诺全库都存在B站对应版本。

## 搜索受限时的公开线索核验

搜索接口返回412后停止该批搜索。可以独立整理已获得的公开资料，不反复请求同一搜索端点：

```sh
# 只从本地缓存的公开合集元数据提取候选，不发起网络请求，不自动批准
python3 scripts/pipeline.py seed-related
# 逐个获取候选详情并核验，不调用B站搜索
python3 scripts/pipeline.py match --existing-only --limit 50 --delay 2
# 对已缓存证据重新应用匹配规则，不发起任何网络请求
python3 scripts/pipeline.py reassess-cached
# 核验公开网页里找到的线索文件，每批最多50个
python3 scripts/pipeline.py verify-leads data/work/web-leads.json --limit 50 --delay 2
```

线索文件是JSON数组，每项包含 `bvid` 或旧式数字 `aid`、公开来源 `url`；可附 `vid` 和 `page` 指定待核验的原片与分P。例如：

```json
[{"bvid":"BV1Ys411k7yQ","vid":"fNk_zzaMoSs","url":"https://www.bilibili.com/video/BV1Ys411k7yQ"}]
```

未指定原片时，只从详情中的原片URL、明确的 `YouTube: ID` 标注，以及分P文件名或有明确标题分段的简介中识别原片ID。网页索引、推荐合集和标题相似度都只提供候选；仍需原片身份、分P、时长和冲突检查。

合集简介中的“上篇／下篇”或“P1／P2”若分别明确标注原片ID，只能将该ID用于相应分P。文件名保留 `[原片ID]` 或末尾 `-原片ID` 时可用于定位；不能从合集总时长或分P顺序猜测。手工指定分P会锁定选择。

`verify-leads` 的详情请求若也出现风控，会锁住后续详情批次。先检查并归档本地 `lead-receipt.json`，确认环境恢复后再由人工触发；不要自动清除锁定或循环重试。执行回执与搜索受阻情况会纳入进展报告。

## 搜索会话修复后的运行约定

2026-11-04已补齐首次搜索前的匿名访客会话初始化，当前恢复验证见 [搜索修复记录](../reports/SEARCH-RECOVERY.md)。搜索自动使用至少3秒间隔和新版缓存空间；访客Cookie仅在进程内保存。

先用 `python3 scripts/search_health.py` 做三条有预期结果的真实查询，再从 `match --limit 5 --delay 3` 开始。需要定位单条断点时使用 `match --vid 原片ID --limit 1 --delay 3`；已完成的旧条目需显式指定 `--recheck` 才会重新处理。

新的 `search_session_version=2` 用于区分旧匿名搜索。不要把旧版本的偏题缓存当作当前搜索结果，也不要因为接口恢复就批量批准候选。再次出现风控时仍立即停下，不自动更换身份、代理或反复重试。

## 检索词与候选预筛

长英文标题在B站可能召回无关结果。可在 `data/search-queries.json` 按YouTube原片ID维护最多两组检索词，例如中文片名、作者加短标题。未配置的原片沿用原片标题和频道名组合。检索词只影响候选搜索，不修改原片标题、作者或匹配批准依据。

已经处理的原片在修改检索词后，需显式使用 `match --vid 原片ID --limit 1 --recheck` 才会重新搜索。程序会比较本次检索词与上次记录，避免把旧查询缓存误作新检索结果。

搜索结果若给出时长，且比原片短到超出既定容差，会先保留为待审候选，暂缓详情请求。这类条目不自动判为失效或不存在，也不会展示。需要人工复核时可用 `inspect` 获取详情。更长的视频可能是合集，不能据此跳过；仍须定位分P。

`--delay` 控制所有网络请求的间隔，默认1.3秒；搜索额外保证至少3秒间隔。初次恢复可用 `--delay 3` 小批验证，稳定后使用默认间隔继续，每批仍不超过50条。

## 定向播放抽查

可用 `PLAYBACK_IDS=原片ID1,原片ID2 PLAYBACK_REPORT=reports/playback-next-batch.json node scripts/playback_smoke.cjs` 检查本批新增内容。不指定ID时仍抽查各类版本。先启动本地预览服务；以视频进度推进为播放证据，缺少指定原片时直接报错。

## 扩大旧待审条目的候选范围

2026-11-04起，每个检索词最多保留20个候选，替代此前的前5个。公开搜索返回的候选只作线索，不会直接批准。已检查过的详情复用缓存，明显过短的新增候选仍暂缓详情请求。

运行 `python3 scripts/pipeline.py match --expand-review --limit 50`，只选择待审且尚未检查前20个结果、或上次补查失败的原片。已确认条目和已完成扩大检查的待审条目跳过。该选项不能与 `--recheck` 或 `--existing-only` 合用；保留原有停止风控、断点及人工审核规则。

`reports/summary.json` 与 `STATUS.md` 分别统计尚需补查、已补查仍待审的数量。已处理或扩大检查都不等于确认成功，存疑内容继续隐藏。

## 从公开缓存整理明确的原片身份线索

运行 `python3 scripts/pipeline.py seed-identities`，离线读取已缓存的公开视频详情与搜索摘要，提取原片URL、明确标注的YouTube ID和分P绑定的ID，仅保留原片库中尚未完成对应详情检查的线索，输出到本地 `data/work/cached-identity-leads.json`。该步骤不发请求、不修改匹配库，也不批准版本。

随后运行 `python3 scripts/pipeline.py verify-leads data/work/cached-identity-leads.json --limit 50`，按相同身份、分P与时长规则核验。可再次离线整理剩余线索，已完成详情检查的候选不会重复输出。接口失败保留状态，详情风控仍会锁住后续核验批次。

搜索摘要中的原片ID只产生线索，核验时必须重新检查完整视频详情；摘要不会绕过身份与时长规则。重复线索优先保留详情中的明确分P定位。

新发现的BV若详情明确返回 `-404`，会保存已失效候选，避免离线整理反复输出同一失效链接。单个失效链接不会将整条原片标成已完成搜索，仍可继续寻找其他版本；网络错误也不会被记录为失效。

## 补充来源证据复核

BV没有直接写原片ID时，仍保持待审。可另行核对原作者网站、课程或会议资料、原片频道的来源说明及嵌入链接，形成能绑定到该原片的证据链，再用 `inspect` 检查可用性、分P、时长及冲突后通过 `review` 记录依据。课程作者、录制日期和讲次等须来自实际读取的资料，不能由模型凭相似标题补全。

2026-11-04两条例子保留在 `reports/manual-identity-reviews.json`。这里的复核由Codex执行，不冒充用户亲自审核；注明来源、对应P及是否逐帧比较。该流程不放宽自动确认规则，也不允许绕过年份、集次、删减或分P归属冲突。

## 可用但不对应的候选

明确核实单P候选的作者、内容身份或来源属于另一部作品时，可用 `review 原片ID BV号 unmatched --page 1 --evidence '实际核对的不同内容身份及来源'` 保存否定结果。必须先 `inspect`，提供依据，并确认该视频可用；不能仅因搜索未命中或标题不相似而批量否定。该操作只否定这条对应关系，不将视频标成失效。

仍有其他待审候选时，原片继续待审；已查候选全部不对应时，原片可记未匹配，但不表示B站绝对不存在其他版本。不能凭单个分P否定整个合集，此命令只接受已检查的单P视频。CID或分P结构变化后，旧否定结果不再自动保留，需要重审。接口错误保持未知，只有明确失效证据才记失效。

## 优先覆盖更多原片

`python3 scripts/pipeline.py match --limit 50 --primary-first` 保留全部搜索候选，先检查语言优先级较高的版本。一条原片有实际确认版本后，同档及更低档的未检查候选暂缓详情请求；更高语言优先级仍检查。排序提示取自搜索结果，仅用于安排请求，不能代替完整详情中的身份、分P与时长核验。页面仍按实际确认版本排序，不承诺已经找齐全部版本。

暂缓候选留在本地待审队列，批次记录 `deferred_candidates`；后续通过 `match --vid 原片ID --limit 1 --recheck` 全面补查版本和可用性。`--primary-first` 不可与 `--recheck` 合用，避免把部分复查当成全面更新。默认不加选项时仍检查全部未检查候选。

普通断连（包括 `RemoteDisconnected`）、接口错误和风控均停止本批并保留断点，不自动重试。普通错误不会标注视频失效，且与风控的停止标志分别记录；只有核对错误原因后才显式恢复。

字幕语言仅凭明确中文、中英、双语等标注进入中文字幕优先档；泛称字幕、CC字幕或字幕组不能自动证明中文字幕。来源身份确认与语言分档分别核验。

明确分P来源也支持同行写法，例如 `P1: 英语原视频 https://youtu.be/原片ID`。只绑定数字指定的P1；P2没有自己的原片ID时不得沿用P1来源，P1也不得匹配P10。全BV链接和相似分P标题仍不足以自动确认。

## 官方来源链补充复核

简介引用官方演讲页而没有YouTube链接时，可以从该官方页面的主播放器或讲者本人明确发布的录像页面补齐原片ID；须保存页面、日期、哈希及实际绑定位置。推荐视频、参考资源中的ID不能代替主视频身份。再核对当前CID、指定分P、可用性、作者/事件、时长和内容冲突后，逐条记入人工复核记录；来源链不能绕过既有检查线，也不能声称做过逐帧比较。

简介文字与链接指向不同作品时，保留待审。错误来源链接可能来自上传者误填，不能仅凭它自动批准或否定视频内容。可选原站探查遇登录要求同样停止，不读取个人凭据，不将其当作视频失效。

## 原站连接中断与运行环境

普通连接错误先保存失败批次，检查原片元数据与B站搜索分别完成到哪一步；没有成功读取元数据时，不将该原片判为失效。每次恢复须有独立回执，按原片ID去重统计，原失败记录保留。风控、登录或412仍按原规则停止。

本机此轮两次普通中断均发生在原站元数据读取，系统Python为3.9.6、LibreSSL 2.8.3。已有Python 3.12.14与OpenSSL 3.5.7通过54项检查及一次单条恢复，后续批次改用此环境。该结果证明新版环境可运行当前流程，尚未证明旧运行环境就是中断根因。

若本机已有uv及Python 3.12，可先定位已安装的解释器，再明确调用：

```sh
YOUTOBILI_PYTHON="$(uv python find 3.12 --no-python-downloads)"
"$YOUTOBILI_PYTHON" scripts/pipeline.py match --limit 50 --primary-first
```

此选择保持证书校验、匿名访问、串行限速与遇错停止。连续运行辅助程序的子进程应使用 `sys.executable`，保证与父进程使用同一解释器；只改变运行环境不能当作永久解决连接问题的依据。

明确写作“中/英字幕”“英/中文字幕”及全角斜线的字幕选项归入中文字幕档；需同时有中文与字幕标注。英/日字幕、泛称字幕不因此进入中文档，配音也不能据此被误标为字幕。

## 文件日期与内容年份

年份核对需要识别紧邻汉字的四位年份，例如“把1930年的电传打字机用作Linux终端”。已识别的 `成片-YYYY-M-D hh:mm:ss` 导出文件名，以及 ` - 个人 - Microsoft Edge YYYY-...` 浏览器录屏尾缀，只提供文件时间信息，不用作内容年份。

原片标题、B站标题或分P中明确属于内容的年份冲突仍进入待审。忽略这两类文件时间不会替代原片ID、分P及完整时长检查，也不会让缺少身份依据的候选通过。修改识别逻辑后，应在当前采集进程结束时，用有效缓存重新评估既有确认及带年份冲突标记的候选，保存变更清单，再构建和验证发布数据。

明确标注翻唱、remix、二创或本作品为AI生成衍生二次创作的候选进入待审；原片链接可能仅是素材署名，不能直接证明内容一致。完整翻译的中文配音不因使用AI而自动排除。该标记也阻止旧人工确认在重查时绕过矛盾；采集中新增规则须待单一写入进程结束后统一重评缓存。
